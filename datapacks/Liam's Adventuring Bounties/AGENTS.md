# Agent instructions: Liam's Adventuring Bounties

Apply these rules to future bounty additions and balance changes unless the user explicitly changes the design. Read this file before editing this datapack. Also consult `minecraft-mods/modpack-development/docs/adventuring-bounties.md` in the adjacent development project for the current reward bands, workloads and implementation details.

## Keep decree mixing disabled

- Preserve `bounty.allowDecreeMixing: false` in `config/bountiful/bountiful.json`, relative to the modpack root (`../..` from this directory). Keep the deployed instance configuration consistent.
- A contract must select its objectives and reward from ONE installed decree. Do not merge all objective/reward pools, inherit generic upstream pools, or turn on mixing to create variety.
- Several decrees may coexist on one board while mixing is disabled. That is the intended source of board variety. Mixing could let an inexpensive gathering or stone commission award restricted magical rewards intended for substantially harder work.
- The datapack alone cannot enforce the global setting or board initialization. Distribute the policy config and Bountiful Contract Fairness companion mod alongside it.

## Enforce dimension progression on every reward

The user requires **Overworld → Nether → Aether → End** progression. This applies to direct rewards and all recursively nested cache/kit contents. A reputation gate, decree name, rare offer or boss fight in an earlier world does not protect a dimension unlock.

- `bounties/progression-review.json` explicitly classifies every reward item and bundle content using installed recipes/encounters. The generator writes `config/bountiful_contract_fairness/dimension_policy.json`; ship that file with companion **1.6.0** and deploy it identically to the instance. Changing this policy requires a full game/server restart because the runtime reads it at startup.
- Nether-gated rewards include Create brass, electron tubes, Deep Seas pressure goggles, Better Nether cincinnasite/agave supplies, Nether foods, ordinary Oakskin Elixirs, the fire runestone, the hogskin-based lesser spell-slot upgrade, netherite and the offered upgrade orbs. Aether and End materials/foods/wood/seeds are staged to their actual region. See the explicit per-item policy; do not infer an unlock from the mod name. Overworld metals, ordinary gear/kit contents, arcane ingots/cloth and inks retain their reviewed Overworld routes. An Ender-themed name alone does not establish an End gate: ender focus uses Overworld-available ender pearls. Mithril has an Overworld deep-cave route in this pack.
- Companion `DimensionContracts.ensure` appends ONE visible mandatory expedition objective after ordinary workload normalization. It requires one reviewed hostile kill while carrying the active bounty, with player and victim in the same dimension at the required stage or later. Nether rewards accept Nether/Aether/End; Aether rewards accept Aether/End; End rewards accept End only. Unknown dimensions never count as later.
- Keep the original one/two base objectives, quotas, timers and fixed reward. The expedition is an explicit additional prerequisite, so a contract may display up to three objectives. Never feed the proof back into shared-budget rounding, drop it to retain a two-line limit, or weaken it at high reputation. If the original hunt is fought in an eligible dimension, one fight can satisfy both objectives on that ONE contract; do not demand another boss kill just for proof.
- Explicit matching hunts take priority over generic expedition-only credit, preserving inventory order within each group. A generic brass commission must not steal a rare boss kill from a matching warrant. Each death still advances at most one carried contract; do not use the upstream criteria-event callback that advances every matching bounty.
- The proof uses native criteria display/progress components with a companion-controlled counter. It deliberately has no criteria pool entry; advancement callbacks must not mass-credit it. Proof state is stored in the bounty and survives native component serialization. Carrying another player's already-progressed paper follows normal Bountiful contract transfer behavior; no persistent global player-unlock state is added.
- `DimensionRewardMixin` checks the exact proof before native `tryCashIn` consumes objectives or pays rewards. Missing/malformed proofs, unknown items, invalid policy and unknown stages fail closed. No ordinary extra requirement is added for an entirely Overworld reward. Return to an Overworld board to redeem after the expedition is allowed.
- Maintain the reviewed proof-hostile IDs; exclude neutral NPCs, merchants and passive animals. Credits require physical presence in the eligible world. Native Bountiful's group/pet credit semantics and ability to fight spawner/transported mobs are unchanged; this is a dimension-access prerequisite, not an entity-origin tracker or portal-lock system.
- Every new reward requires a stage classification and rationale. Nested contents inherit the highest stage. Classification does not authorize adding an otherwise forbidden reward. The supported future classifications for enchanted gravitite (Aether) and shulker shells (End) are not new reward entries.
- Preserve **all eight** isolated server PASS markers, including `BOUNTIFUL_DIMENSION_PASS`. Cover all four dimension boundaries, later-stage acceptance, unknown/missing policy behavior, nested caches, neutral exclusions, explicit-hunt priority, single-contract credit, proof persistence, proof retention after normalization and actual guarded redemption. Keep the test-only flat Aether dimension and all fixtures out of the production JAR.
- New-world scope remains in force: do not migrate old boards, rewrite held bounties or edit player saves. Use newly generated contracts after the required restart. Existing gated contracts without the new proof cannot be redeemed; do not bypass the guard to keep them usable.

- The implementation lives in the adjacent `minecraft-mods/bountiful-contract-fairness` project: `StarterDecrees.java` defines roles/candidates; `BoardDecreesMixin.java` handles fresh-board initialization, offer rotation and normal save/reload.

- `StarterDecrees.Role` lists the eligible starter candidates. Add a new decree to exactly one starter role only when its tasks and rewards are suitable for an ordinary new-world village board. Set its catalogue `can_spawn` appropriately; that flag alone does not add it to the companion mod's starter selection. Nonstarter/specialist decrees do not need a companion role entry.

Player removals/replacements must remain respected across ticks and save/reload. Do not repeatedly refill intentional empty slots or directly edit player-world files as a routine content update.
